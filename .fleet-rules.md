# Standing rules

Binding for all work in this repo. Generated by `fleet.py rules sync`: do not edit by hand; project rules go in CLAUDE.md.

Data-driven is the base: behaviour comes from declared data like manifests, specs, schemas, registries and config. Event-driven is the required style at the seams, where parts must stay unaware of each other (rule 5). Main execution paths are not event-driven. They dispatch by id through a registry, or run a planned graph or pipeline.

How to use this guide
- It covers all implementation: everything the fleet builds (services, web apps, tools and games), helper and one-off scripts, tests, and the fleet's own code. Apply the rules the project has a use for. Lines marked [service] need a server, tenants or outbound calls; lines marked [game] need a game engine. A jam game has no tenants; a command-line tool has no frame budget.
- Hard rules, at any project size: content and tuning as data (1), no ladders (3), outside input is data and secrets stay out (10), evidence for every claim (14). The rest are strong defaults: when a simpler shape fits the goal better, take it and write one line of why where the next reader will see it.
- Reviewers: report a rule only where the change breaks it, with `file:line`. A broken hard rule is a MAJOR; a bent default is a MINOR unless it will block the goal. A missing test or boundary check never holds back a first playable.
- Rule numbers are stable: decisions and config cite them. New rules get new numbers.

Core style

1. Declare it, don't code it
- Capabilities, permissions, routes, themes, model choices and pipeline steps are written as data: manifests, specs, JSON or YAML.
- Code reads that data. Adding a tier, theme or role means editing data, not writing new logic.
- Code holds the algorithm. Numbers, thresholds, colors, wording and prompts live in config or templates.
- [game] The config is the engine's own data asset, one per scenario or profile, referenced by its consumer: ScriptableObject in Unity, data assets and DataTables in Unreal. It is not JSON read from disk at run time; JSON is only an import/export interchange for agents, MCP and Python tools (human 2026-10-14, after a shared JSON budget key broke an unrelated perf test).
- [game] What a reviewer cannot read, it cannot judge. Logic stays in text (code, text data), never only inside a binary asset such as a visual script, scene or level file.

2. Each fact has one owner
- Every vocabulary or contract lives in exactly one file or registry. Everything else reads, generates or mirrors from it.
- Generated files are never edited by hand. A drift test fails CI when a mirror falls out of sync.

3. Registries instead of branching
- A new provider, engine, theme or tool means registering a new module. Don't add an if/elif or switch case.
- No nested if/else chains, and no long if/elif/else-if or switch ladders over a kind, mode or state (human 2026-10, hard rule again 2026-11-10). Preferred, in this order: data-driven (the case is a config/ScriptableObject/registry entry), a functional map (key -> handler table), an enum state (an explicit state enum with a transition table, not boolean flags). A new case is a new entry, not another branch. Hard-coded if/else logic over values (names, ids, thresholds, tiers, special cases) is the same ladder: put the values in a table or map and keep one generic code path (human 2026-11-14: for all implementation). Guard clauses (early return) are fine; a single if/else on one condition is fine. Reviewers report a nested chain or a ladder as a MAJOR.
- Lookup is by a stable identity key, like (owner, operation).
- A search index is only for discovery. The registry in memory is the live truth.

4. Contracts first, changes additive
- Change the schema or interface before the code.
- Never rename existing fields. Add alias keys or an adapter step instead.
- Every input gets validated against a schema. Don't trust validation done on the client.

5. Event-driven at the seams (expanded 2026-11-15)
- The seams between parts are event-driven: the part that changes state publishes a typed domain event, and the parts that only react (UI and HUD, audio, effects, scoring, achievements, telemetry, notifications) subscribe to it. The publisher never calls them directly and never knows who listens.
- One typed event bus per app or game, not ad hoc delegates or callbacks wired between siblings. [game] Gameplay emits events such as StrikeDetonated, PhotoTaken, UnitDied, SectorEnded; the HUD, sound, music intensity and score react.
- Events are typed schema models (not loose dicts) that carry ids and values, never live object references, so they can be logged, replayed, sent over the network and tested.
- An event catalog (a registry) lists every event name, its schema, its publisher and its subscribers; a test fails when code publishes or subscribes to an event the catalog does not list.
- Handlers are idempotent and cheap: no blocking work and no long chains of events triggering events. A handler that needs heavy work queues it.
- Never use events to read state back. When the caller needs the answer, make a direct call. Main execution paths and hot loops (per frame, per voxel, per request) stay direct calls or registry dispatch.
- [service] Outbound delivery is at-least-once: a cursor advances only after the receiver confirms. Writes are idempotent through a client request id, so retries are safe.

Boundaries

6. Hard module boundaries, enforced by tests
- Siblings never import each other. They talk through dispatch by id, a service locator, or events.
- Extensions never reach into core internals. They use narrow interfaces.
- Import-boundary tests in CI fail any bypass.

7. Pure core, side effects at the edge
- Domain logic is pure functions over (state, time, randomness), so it runs in a test without the engine, the network or a clock.
- I/O, HTTP and storage happen in one wiring layer.
- [service] Only one component makes outbound calls. Data access stays in a store or repository layer, never in a request handler.
- Async code never blocks: blocking calls go to a thread, and fire-and-forget tasks are supervised.

8. Lifecycle, pooling and performance (loosened 2026-11-10)
- Prefer clear phases: load (declare and register, little or no I/O), ready (connect, warm caches, prewarm pools and shaders), unload (clean up, even when it fails). Bend them when a simpler shape fits.
- Pool what is created often: objects, effects, projectiles, buffers and connections are reused, not allocated per use; pools prewarm before the first hot moment and stay bounded.
- Optimize where it shows: measure first (frame time, draw calls, allocations, latency), fix the hot path, keep budgets from the goal. Cache, batch, instance and cull before adding hardware cost.
- Background loops prefer one shared worker plus a registry over hand-rolled loops, when one exists.
- Hot reload, when supported, works by unloading and loading again.

9. Deterministic gates, not hard locks (human 2026-11-10)
- Agents are checked by deterministic flow, not fenced in: lint rules, specs and schemas, the verify command, tests and budgets decide whether work passes. An agent may touch what it needs; a red gate, not a lock, stops bad work.
- Specs are data and are validated when written: an invalid spec is rejected at write time; a stored spec that no longer parses is skipped and logged, never crashing the system.
- Lessons become checks: a recurring mistake turns into a lint rule or a spec field, so the gate learns instead of adding a new restriction.
- Product security stays strict: user-facing permission checks, auth and secrets still default to deny and fail closed.

10. Outside input is data, not instructions
- User input, scraped pages, LLM output and browser scores are untrusted. Validate, clamp and sanitize them.
- Secrets never go into git, logs or output, and URLs that carry tokens are redacted.
- [service] Outbound URLs get checked for SSRF, including on redirect.
- [service] Every query filters by tenant.
- [game] A networked game trusts only the host: clients send intent, the host validates it and owns the state.

11. The model owns the direction, limits stay reasonable (human 2026-11-10)
- The model decides the direction and the design until feedback arrives (review, play test, the human). Feedback steers it; rules do not pre-decide it.
- Cost and resource limits exist but are set at a reasonable price for the goal: budgets, caps on fan-out, loops and retries are generous safety nets, not tight cuts.
- When something fails or drifts, the agent self-heals (retry, rethink, replan from what it learned) and evolves over time; do not force-cut scope or stop work just to stay under a number.

Reliability and process

12. Errors become values at the boundary
- One wrapper turns failures into structured error results with context. Nothing raw leaks to the client.
- Recoverable errors get one retry, then a replan that remembers the failure.

13. State has one owner layer
- Server data, shareable URL state, device preferences and transient UI state each live in one layer, never copied across.
- Saves and migrations carry a version, give new fields a default, and keep history.
- User data and system files stay apart, so updates never overwrite personal changes.

14. Rules backed by tests, docs agents read
- Every rule has a test, a CI check or a generator behind it. A rule that is only written down fades.
- Agent guidance lives in files loaded automatically and gets updated after each structural change.
- Verification needs evidence. A check that couldn't run is reported as blocked, never as a pass.
- A number proves only what it measured: name the scope, the build and the runtime. A look or a feel is proven by a frame or by playing, never by a metric.

In short: data declares what exists, registries resolve it, contracts guard it, events decouple it, tests enforce it.

## Web rules

- UI text, themes, routes and feature lists are data, not branches in components.
- Keep state in one owner per fact; derive the rest.
- Validate every outside payload at the boundary.
- Pin dependency versions, and add none without a reason in the handoff.
